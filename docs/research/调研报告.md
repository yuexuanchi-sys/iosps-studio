# iOS 生日礼物 App（P图 + 视频剪辑）前期调研报告

> 调研时间：2026-11-20 ｜ 设备目标：iPhone 14（iOS）｜ 调研性质：**只做资料收集与浅分析，不写代码**
> 事实标注：文中「已核实」= 2026-11-20 直接抓取 GitHub API / Apple 官方页面确认；「待核实」= 未拿到一手证据，需后续确认。

## 0. 摘要（先看这一页）

1. **你看到的"把 PS 重构成很小程序并开源"的项目，最可能是 Compositor**：Swift + MIT，GitHub 18,763★，安装包约 **8.9MB**，2026-09 发布后爆火，**但只有 macOS 版**。它和同类项目（PhotoCraft、Graphite、PhotoSplice）都**不能直接装到 iPhone 上**——它们是桌面/Web 技术栈，价值在于"架构教材 + 功能清单参考"。
2. **iOS 上不存在"下载即用的全功能开源 P图+剪辑 App 底座"**。正确路线是：**原生 Swift 开发 + 组合若干 MIT/Apache 开源库 + 自研编辑界面**，这恰好也是小团队能做出来的方案。
3. **照片编辑**推荐底座：`Core Image + Metal`（开源可参考 **Brightroom**、**MetalPetal**）+ 相册选择用 **ZLPhotoBrowser** + 抠图用 **Vision** 系统能力（iOS 17+ 前景分割）。滤镜、文字、贴纸、涂鸦、马赛克、拼图需要自研（工作量可控）。
4. **视频剪辑不需要 FFmpeg**：`AVFoundation + Core Image` 足够覆盖裁剪/拼接/转场/字幕/BGM/画中画/变速/导出。**ffmpeg-kit 已于 2025 年退役（仓库已归档，LGPL-3.0）**，不要作为新项目底座。
5. **最大现实障碍不是技术，而是"你只有 Windows"**：做 iOS App 必须有 macOS 环境。可行组合 = **$99/年 Apple 开发者账号 + 云端 Mac/CI 构建（Codemagic、GitHub Actions、云 Mac 租用）+ TestFlight 体验 + Unlisted（链接分发）长期上架**。预算约 **¥1000–3000/首年**，不需要买 Mac。
6. **"简单易用 + 绝大多数效果"的正确解法是"模板化 + 一键出片"**：用生日回忆短片模板、一键美颜、一键抠图、预设滤镜覆盖 80% 使用场景，而不是把 PS/PR 的复杂面板搬到手机上。
7. **建议产品形态**：双层结构——「生日礼物层」（主页/回忆/彩蛋）+「实用工具层」（修图/剪辑/回忆短片），先做 3–6 周能完成的 MVP，再迭代。**当前阶段建议只做资料与方案确认，不急于写代码**。

## 3. iOS 图像编辑（P图）资料分析

### 3.1 原生能力底座（不需要第三方库就能做很多事）
| 技术 | 能实现的效果 | 备注 |
|---|---|---|
| **Core Image（CIFilter）** | 亮度/对比度/曝光/高光阴影/饱和度/色温/锐化/降噪/模糊/暗角/黑白/复古/色调分离/风格化等 200+ 内置滤镜；自定义 `CIKernel`（Metal 语言）做任意像素效果 | iOS 自带、GPU 加速、导出方便，是照片编辑主力 |
| **CIContext + CIImage** | 非破坏性滤镜链、离屏渲染、导出 JPEG/HEIC/PNG | 注意色彩空间（iPhone 照片是 Display P3）与方向（EXIF）处理 |
| **Metal / MetalPetal** | 实时预览、复杂多滤镜合成、视频逐帧处理 | MetalPetal（MIT）封装了 Metal 图像/视频处理，省大量底层代码 |
| **Vision** | 人脸关键点/人脸检测（美颜定位）、人物分割、**前景实例分割**（iOS 17+ `VNGenerateForegroundInstanceMaskRequest`，抠图神器）、OCR | 系统能力、免费、隐私好、iPhone 14 可跑 |
| **VisionKit** | 系统级"主体提取"交互 | iOS 16+，可参考其抠图体验 |
| **Photos / PHPicker** | 相册多选（无需相册权限）、保存到相册（add-only 权限）、Live Photo/视频选择 | `PHPickerViewController` 已是系统组件，不必依赖第三方选择器 |
| **Photos 编辑扩展** | 让 App 出现在系统相册"编辑"里 | 加分项，非必须 |
| **Core ML** | 可跑自定义模型（抠图、超分、风格化、老照片修复） | 模型体积/速度要评估；iPhone 14 可跑轻量模型 |

> 关键结论：**iOS 原生能力已覆盖 80% 的 P图需求**，开源库主要解决"UI 更快搭出来"和"特定算法"。

**照片编辑里"没有现成开源库、必须自研"的部分**（工作量都不大，但需要设计好）：
- 图层化 P图界面（文字/贴纸/涂鸦/马赛克/多图合成）；拼图模板（九宫格/自由拼/长图拼接）；
- 滤镜预设系统（调整参数 + 3D LUT `.cube` 文件，`CIColorCube` 加载）；
- 美颜/液化（磨皮可用双边滤波/导向滤波 + 混合；瘦脸大眼用局部网格变形 `CIWarpKernel` 或 Metal）；
- 模板化排版（朋友圈/生日贺卡/日签，文字+图片+贴纸组合，本质是 JSON 模板渲染）。

### 3.4 可嵌入 WKWebView 的 Web 图像编辑器（备选路线，不推荐做主方案）
| 项目 | 链接 | License | ★ | 状态 | 评价 |
|---|---|---|---|---|---|
| tui.image-editor | <https://github.com/nhn/tui.image-editor> | MIT | 7,666 | **已归档（2023-11）** | 功能全（裁剪/滤镜/文字/图形/蒙版），但已停维护，不建议新项目依赖 |
| miniPaint | <https://github.com/viliusle/miniPaint> | GitHub 识别为 **NOASSERTION**（需人工核对 LICENSE） | 3,502 | 活跃（2026-11） | 类 PS 的 Web 编辑器，功能很强；许可需先确认 |
| Fabric.js | <https://github.com/fabricjs/fabric.js> | MIT | 约 3 万 | 活跃 | 图形画布库，适合做"贴纸/文字/涂鸦"轻交互 |
| Konva.js | <https://github.com/konvajs/konva> | MIT | 约 1.2 万 | 活跃 | 2D Canvas 交互框架，同上 |
| Photopea | <https://www.photopea.com> | **非开源** | — | 商业免费 | 只能当竞品参考，不能嵌入商用 |

**WKWebView 嵌入的真实限制（重要）**：
- iOS Safari/WKWebView 的 Canvas 有**面积上限（约 1600 万像素级别）**，iPhone 14 的 4800 万像素原图无法直接全尺寸编辑，必须先降采样；
- 桥接要用 `WKScriptMessageHandler`，把图片以 base64/临时文件传入，导出再回传，**大图内存压力大、容易崩**；
- 触控手势与原生编辑体验有割裂，Undo/Redo、相册读写、视频处理都要额外桥接；
- **结论：Web 编辑器可作为"快速原型/彩蛋页面"，不适合作为主照片编辑器**。

|---|---|---|
| **MVP** | Core Image 自研滤镜/调整 + ZLPhotoBrowser（相册+基础编辑）+ Vision 抠图 + 自研文字/贴纸/马赛克/拼图 | 2–4 周可出可用版本 |

## 4. iOS 视频剪辑资料分析

### 4.1 AVFoundation 能覆盖的剪辑能力（系统原生、免费、性能好）
| 能力 | 对应 API/做法 |
|---|---|
| 多段视频导入、排序、裁剪、分割、删除 | `AVMutableComposition` + `AVAssetExportSession` |
| 变速（0.25x–4x）、倒放 | `scaleTimeRange`；倒放需逐帧重排（可选） |
| 转场（淡入淡出/叠化/推拉/擦除） | `AVMutableVideoComposition` + 自定义 `AVVideoCompositing`（Metal/Core Image 渲染） |
| 画面滤镜/LUT/调色 | 同上，逐帧 `CIImage` 处理 |
| 文字/字幕/贴纸/画中画 | `AVMutableVideoComposition` 的 layer instruction + Core Animation / Core Image 叠加；或自定义 compositor 绘制 |
| 背景音乐、原声混合、淡入淡出、录音配音 | `AVMutableAudioMix` + `AVAudioEngine`（录音） |
| 画面比例（9:16/1:1/16:9）、裁剪、旋转、镜像 | layer instruction 的 `transform` + `cropRectangle` |
| 实时预览 | `AVPlayerItem(videoComposition:)` + `AVPlayerLayer`（最简单）；或 `AVPlayerItemVideoOutput` 自绘 |
| 导出 1080p/4K、H.264/HEVC | `AVAssetExportSession`（预设/自定义）或 `AVAssetReader`+`AVAssetWriter`（完全控制） |
| 播放速度/流畅度 | iPhone 14 硬件编码器足够 1080p 实时预览与快速导出 |

### 4.3 FFmpeg 现状（重点核实）
- **已核实**：`arthenica/ffmpeg-kit` 仓库 **archived = true**，最后推送 2026-07-02，License 为 **LGPL-3.0**。它曾是 iOS/Android/Flutter/RN 上最常用的 FFmpeg 封装。
- 退役后的现实：
  - 预编译二进制不再维护，新 Xcode/iOS 版本兼容性要自己解决；
  - 社区有 fork 和"自行编译 FFmpeg"的方案（如自己写 build script 编译 xcframework），但要自己承担升级、体积、符号冲突；
  - **LGPL 合规**：动态链接 + 提供替换库的方式 + 声明；若静态链接且带 GPL 组件，App Store 分发有法律风险（历史上 VLC 就因此下架过）。
- **判断：生日 App 完全不需要 FFmpeg**。剪映级的基础剪辑（裁剪/拼接/转场/字幕/BGM/画中画/变速）用 AVFoundation + Core Image 就够；只有"特殊编码格式（MKV/AVI/字幕文件/冷门编码）导入"才需要 FFmpeg，而目标用户是 iPhone 拍的 HEVC/H.264 视频，不存在这个问题。

### 4.4 "照片 + 音乐一键生成回忆短片"的实现思路（本项目的核心卖点）
1. **模板定义**：JSON 描述每一幕（照片数量/时长/转场/Ken Burns 方向/文字/滤镜/音乐段落）；
2. **自动排版**：按音乐节拍或固定时长分配照片长度；照片做 Ken Burns（缓慢推拉摇）避免呆板；
3. **渲染合成**：Core Image 逐帧渲染（照片→视频帧）+ 转场叠加 + 文字图层，`AVAssetWriter` 写入 H.264/HEVC；
4. **导出**：1080p 30fps 优先（速度快、体积小、够清晰），可选 4K；
5. **工程实现要点**：进度回调、后台继续、失败可恢复、草稿自动保存；渲染用 `AVAssetWriter` + `CVPixelBufferPool` 控制内存。
6. 参考：Cabbage 的 composition 组织方式 + 开源项目里 "Ken Burns/photo slideshow" 的常见做法（多为自研，代码量不大）。

### 4.5 iPhone 14 上的性能边界（工程估算，非实测——待实测）
| 场景 | 预期 | 建议 |
|---|---|---|
| 1080p 30fps 预览（3–5 段、带滤镜） | 流畅 | 预览用 720p/1080p 代理，导出用原分辨率 |
| 4K 30fps 预览 | 可能掉帧/发热 | 预览降分辨率，导出再上 4K |
| 1–3 分钟 1080p 短片导出 | 约几十秒到 2 分钟（取决于滤镜/转场） | 显示进度、可取消、避免后台被系统杀死 |
| 长视频/多轨/大量贴纸 | 内存与 GPU 压力大 | 限制轨道数、贴纸数；分阶段渲染 |
| 发热 | 连续剪辑 10 分钟以上明显 | 自动降预览帧率，提示用户 |

### 4.6 视频方案推荐
- **基础剪辑**：AVFoundation（`AVMutableComposition` + `AVMutableVideoComposition` 自定义 compositor）+ Core Image 滤镜；
- **预览**：`AVPlayer` + `videoComposition`（实现简单，性能可接受）；
- **导出**：`AVAssetExportSession`（自定义 videoComposition）优先，复杂需求用 `AVAssetReader/Writer`；
- **UI 参考**：Cabbage 的合成模型 + PryntTrimmerView 的时间轴交互 + 剪映/InShot 的"底部大按钮 + 时间轴拖拽"布局；
- **明确不做**：多轨专业时间轴、关键帧曲线、逐帧调色、字幕逐字动画——这些是 VideoLeap/剪映专业版级别的工作量，不适合礼物 App 的 MVP。

### 5.3 "极简易用"的设计原则（给开发/设计阶段的约束）
1. **首屏三入口**：`回忆`、`修图`、`剪辑`——最多加一个"更多/设置"；
2. **模板优先**：用户先选模板，再换照片/改文字，最后导出；专业参数折叠在"高级"里；
3. **三步内完成一件事**：修图 = 选图 → 选预设/调整 → 保存；剪辑 = 选素材 → 选模板/顺序 → 导出；
4. **大按钮、底部操作区、单手可达**：主操作永远在屏幕下方 1/3；
5. **即时反馈**：所有调整实时预览；长按对比原图；操作有微动效；
6. **永不丢内容**：自动保存草稿、退出重进可恢复、撤销/重做至少 20 步；
7. **空状态引导**：没有照片时给出示例/引导，不让用户面对空白；
8. **中文文案与字体**：默认中文字体（苹方），祝福文案要有"人味"（不要模板腔）；
9. **性能兜底**：大图先显示缩略图、后台渲染、进度条、可取消；
10. **无障碍**：VoiceOver 标签、动态字体、对比度；深色模式跟随系统。

## 6. 技术方案对比与推荐

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 全原生 Swift/SwiftUI** | SwiftUI 界面 + Core Image/Metal + AVFoundation + 少量开源库 | 性能最好、体验最好、体积小（可做到 20–50MB）、长期可维护 | 需要学 Swift/图像/音视频开发；工作量最大 | **✅ 推荐** |
| B. 原生壳 + WKWebView 编辑器 | 原生界面 + Web 图片编辑器（miniPaint 等） | 开发快、Web 生态现成 | Canvas 分辨率/内存限制、体验割裂、视频处理弱、许可需核对 | ❌ 不推荐做主方案（可做彩蛋/原型） |
| C. Flutter / React Native 跨端 | 一套代码多端 | 你有 Windows 也能写；云端构建成熟 | 图像/视频编辑插件生态弱，重算法要写原生桥接，性能损耗 | ⚠️ 可行但绕路；本项目只有 iOS 一个目标，不值得 |
| D. 改造桌面开源项目（Compositor/PhotoCraft） | 把 macOS/Rust 代码移植 iOS | 功能现成 | 技术栈/UI 差异巨大，移植成本高于重写 | ❌ 不可行 |

**推荐方案 A 的具体技术栈（2026-11 版本）**：
- 语言/UI：**Swift 6 + SwiftUI**（复杂画布用 `UIViewRepresentable` 包裹 UIKit/Metal 视图）；
- 图像：**Core Image**（主力）+ 自研 Metal kernel（复杂效果）+ 可选 **MetalPetal**（渲染管线）；
- 视频：**AVFoundation**（编辑/预览/导出）+ Core Image；
- 相册：**PHPicker**（系统）或 **ZLPhotoBrowser**（更顺手的中文 UI）；
- 抠图/人脸：**Vision**；
- 存储：本地 `Codable` 工程文件 + `FileManager`，**不建后端、不做账号**；
- 最低系统：建议 **iOS 17.0**（覆盖 iPhone 14 且能用前景分割抠图等新 API；若想更广覆盖可降到 iOS 16，但抠图能力弱）；
- 第三方依赖（SPM）：**尽量少**——ZLPhotoBrowser（可选）、Brightroom/MetalPetal（可选）、其余自研，降低停更风险与审核复杂度。

## 7. 从 Windows 把 App 装到朋友 iPhone 上（最现实的章节）

### 7.1 硬性事实（已核实）
- 开发 iOS App 必须用 **Xcode**，Xcode 只能跑在 **macOS** 上；
- 当前（2026-11）最新稳定版为 **Xcode 27.x**，要求 **macOS Tahoe 26.6+**，配套 **iOS 27 SDK**，可部署到 **iOS 15–27**；
- 也就是说：**Windows 无法直接开发/签名 iOS App**；Hackintosh/虚拟机违反 Apple 许可协议，且新系统几乎不可行，**不建议**。

### 7.2 四条可行路径（按推荐度）
| 路径 | 你怎么做 | 成本 | 体验 | 适合你吗 |
|---|---|---|---|---|
| **① 云端 CI 构建（最推荐）** | Windows 上用 VS Code 写 Swift/或让 AI 生成代码 → 推 GitHub → **Codemagic / GitHub Actions（macOS runner）/ Xcode Cloud** 自动构建并上传 TestFlight | 开发者账号 $99/年；Codemagic 有免费额度（以官网为准），GitHub Actions macOS 分钟按 10 倍计费 | 无需 Mac，适合持续迭代；初期配置 1–2 天 | ✅ 最适合 |
| ② 租云 Mac | MacinCloud / MacStadium / AWS EC2 Mac / Scaleway 远程桌面，装 Xcode 开发 | 约 $20–100/月（按配置） | 有真实 Mac 体验，但远程操作有延迟 | ✅ 备选（预算够） |
| ③ 借/买一台 Mac | 借朋友的 MacBook，或二手 Mac mini（M1 约 ¥2000–3000，以市场价为准） | 一次性 ¥2000+ | 体验最好、调试最方便 | ✅ 若有预算/渠道 |
| ④ iPad + Swift Playgrounds | 在 iPad 上写 SwiftUI App，直接提交 App Store Connect | 需要 iPad + $99 账号 | 只适合简单 App；复杂工程/自定义 Metal/第三方库受限 | ⚠️ 简单版可考虑 |

> **对你的建议**：**路径①**。你不需要买 Mac：账号 $99 + Codemagic 免费额度即可完成"构建→上传 TestFlight→朋友安装"的闭环。若你想本地调试/改 UI 更方便，再考虑二手 Mac mini。

### 7.3 分发方式对比（关键：让礼物"长期可用"）
| 方式 | 有效期 | 人数/范围 | 成本 | 审核 | 适合送朋友吗 |
|---|---|---|---|---|---|
| **App Store 公开上架** | 长期（账号有效期内） | 全球 | $99/年 | 需审核（1–3 天），可能被拒 | ✅ 可用，但会公开可见 |

## 8. 合规与风险清单

### 8.1 开源 License 矩阵（上架 App Store 视角）
| License | 能否用于闭源商业 App | 上架 App Store 注意点 | 结论 |
|---|---|---|---|
| MIT / BSD-2 / BSD-3 | ✅ 可以 | 保留版权声明与许可文本（App 内"开源许可"页） | ✅ 放心用 |
| Apache-2.0 | ✅ 可以 | 保留声明、NOTICE、专利条款；修改文件需标注 | ✅ 放心用 |
| MPL-2.0 | ✅ 可以（文件级） | 修改过的 MPL 文件需公开源码 | ⚠️ 尽量不修改其源码 |
| LGPL-2.1/3.0 | ⚠️ 有条件 | 动态链接 + 允许用户替换库 + 声明；静态链接有争议 | ⚠️ 能不用就不用（如 FFmpeg） |
| GPL-2.0/3.0 | ❌ 事实困难 | 与 App Store 分发条款冲突（需提供完整源码/重链接权利） | ❌ 不要用 |
| AGPL | ❌ | 网络使用即触发开源义务 | ❌ 不要用 |

**本项目用到的库**：Brightroom（MIT）、MetalPetal（MIT）、ZLPhotoBrowser（Apache-2.0）、TOCropViewController（MIT）、GPUImage3（BSD-3）、Cabbage（MIT）、PryntTrimmerView（MIT）——**均为宽松许可，可放心使用**；需在 App 内放"开源许可"页。

### 8.2 素材版权（生日 App 也必须注意，尤其要上架）
| 素材 | 风险 | 建议 |
|---|---|---|
| 字体 | 商用字体（如方正、微软雅黑）不能随 App 分发 | 用 **Google Fonts（OFL）** 或系统苹方 |
| BGM/生日歌 | 流行歌曲、Apple Music 下载曲有版权/DRM | 用 **CC0/CC-BY 免版权音乐**（Pixabay/Freesound）或自己弹唱录制；用户从本地导入音乐属于用户行为，但**内置曲库**必须有授权 |
| LUT/滤镜 | 网上 LUT 可能来自商业预设包 | 自己调/生成 LUT，或使用明确授权的 LUT |
| 贴纸/插画 | 表情包、明星图、影视截图侵权 | 自绘/AI 生成/CC0 素材 |
| 朋友照片/肖像 | 私下礼物风险低，但上架审核时不可用他人肖像做宣传素材；App 不得内置朋友照片作为默认内容 | 内置内容用无版权示例图，朋友照片由用户自己导入 |

### 8.3 App Store 审核要点（上架必看）
- **4.2 最低功能性**：纯"生日贺卡"或只有几个页面的 App 容易被拒；**把它做成真正可用的修图/剪辑工具**就稳（这也是"P图+剪辑"功能的价值）；
- **5.1 隐私**：相册/相机/麦克风用途描述（`NSPhotoLibraryUsageDescription`、`NSPhotoLibraryAddUsageDescription`、`NSCameraUsageDescription`、`NSMicrophoneUsageDescription`）必须写清楚；
- **2.5 私有 API**：只用公开 API（原生框架 + 正规开源库）；
- **5.2.5 音乐/媒体版权**：内置 BGM 必须有授权；
- **1.2 用户生成内容**：若未来做分享社区，需要举报/屏蔽机制；本礼物 App 不做社区则无此问题；
- **隐私清单** `PrivacyInfo.xcprivacy`（2024-05 起）：若使用 UserDefaults、文件时间戳等"required reason API"，需声明原因；第三方 SDK 需带隐私清单（选 MIT 小库通常无问题）；
- **年龄分级**：含用户生成内容的工具类一般 4+；内置音乐/社交功能需如实填写；
- **App 隐私标签**：若纯本地处理、无统计 SDK，可勾"不收集数据"，最省事也最让朋友放心。

### 8.4 生日礼物特有风险
1. **时效性**：生日日期固定，功能必须倒排；**先保证能跑，再追求全面**；
2. **朋友手机系统版本未知**：最低支持 iOS 17 兼容性最好（iPhone 14 用户大多已升级）；
3. **文件体积**：内置大量模板/音乐/贴纸会让 App 变大，建议模板云端下发或精简内置（注意：云端内容需网络，礼物场景建议全内置但控制体积）；
4. **崩溃/发热**：视频导出最容易出问题，必须做进度/取消/失败提示；
5. **法律**：私下送人风险极低；若要公开上架或装到多人手机，按 8.2/8.3 处理。

## 9. 结论与下一步建议

### 9.1 一句话结论
**不要试图"改造现成开源项目"，而是用 iOS 原生技术栈（Core Image/Metal + AVFoundation + Vision）组合 MIT/Apache 开源库，做一个"生日礼物 + 轻量修图 + 一键回忆短片 + 基础剪辑"的 App；开发环境用"$99 账号 + 云端构建"，分发用"TestFlight 先体验 + Unlisted 链接上架"。**

### 9.2 建议的推进路线
| 阶段 | 目标 | 产出 | 时间 |
|---|---|---|---|
| 第 0 步（现在） | 确认需求边界与预算 | 本报告 + 你回答 9.3 的 5 个问题 | 1–2 天 |
| 第 1 步 | PRD + 原型 | 功能清单、页面流程、视觉风格（生日主题） | 3–5 天 |
| 第 2 步 | 云端环境与账号 | 开发者账号、GitHub 仓库、Codemagic 构建跑通 | 3–7 天 |
| 第 3 步 | MVP 开发 | P0 功能 + 回忆短片模板 | 3–6 周 |
| 第 4 步 | 内测与礼物准备 | TestFlight 给朋友试、准备祝福内容/彩蛋 | 1 周 |
| 第 5 步 | 正式分发 | Unlisted 上架或 TestFlight 长期方案 | 3–7 天 |

### 9.3 需要你确认的 5 个问题（决定方案细节）
1. **朋友生日是哪天？**（决定倒排工期与 MVP 范围）
2. **你打算自己写代码（可以用 AI 辅助），还是主要找人做？**（决定技术方案复杂度与工作量分配）
3. **$99/年开发者账号可以接受吗？**（这是"长期装到朋友手机 + 上架"的必要条件；如果不接受，只能走 TestFlight 90 天/网页版）
4. **你希望"只在朋友手机上长期存在"，还是"公开上架让更多人用"？**（决定 Unlisted vs 公开 App Store）
5. **朋友 iPhone 14 当前的 iOS 版本？你身边有没有 Mac 可以借？**（决定最低支持版本与开发路径）

### 9.4 本报告的边界
本报告只做资料收集与浅分析，**没有写任何代码、没有创建工程**。确认方向后，下一步可以继续产出：PRD、页面原型、Xcode 工程骨架、云端构建配置、以及 MVP 的详细任务拆分。
